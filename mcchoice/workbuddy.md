# WorkBuddy 对话上下文

本文件供 WorkBuddy 专项奖励评审使用，记录 McChoice 在 WorkBuddy 中的真实交互过程。

## 项目与 WorkBuddy 的关系

McChoice 是基于 WorkBuddy 智能体平台开发并验证的开源项目：

- 项目**通过 WorkBuddy 完整开发**，从能力盘点、架构设计、编码、测试到文档产出
- 项目提供标准 Agent Skill 定义（`skill/SKILL.md`），**可在 WorkBuddy 中直接加载使用**
- 项目的开发环境已配置麦当劳 MCP Server（`mcd-mcp` → `https://mcp.mcd.cn`），
  McChoice 的集成验证即在该环境中完成

## 开发过程中的关键决策

### 决策一：先做能力盘点，再写代码

在动手实现前，通过 MCP 协议握手（`initialize` + `tools/list`）
拉取服务端全部 35 个工具的清单与入参 schema，并逐个实测关键工具。

这一步发现了任务书中一处会导致项目跑不通的假设：

> 任务书描述为「调用菜单工具获取商品名称、价格」，
> 但实测 `query-meals` 只返回 `code` 与 `tags`，既无名称也无价格。

如果不先验证而是直接按假设实现，会导致整个项目的价格逻辑建立在错误前提上。

### 决策二：价格只能来自 calculate-price

基于实测结论，项目确立「所有价格必须来自 `calculate-price` 真实试算」的原则。
这成为项目最核心的技术特征，也是本项目区别于普通菜单查询机器人的地方。

### 决策三：安全边界通过代码强制，而非靠自觉

`McDClient.FORBIDDEN_TOOLS` 在代码层面拦截 7 个交易类工具，
配合单元测试验证。这比在提示词里写"请不要下单"可靠得多。

## 开发中真实发现并修复的问题

这些问题都是通过真实调用麦当劳 MCP 才发现的，模拟数据无法暴露：

| 问题 | 发现方式 | 修复 |
| --- | --- | --- |
| `calculate-price` 字段名是 `productCode`/`quantity` 而非 `code`/`count` | 实测报 `code=600010` | 按真实 schema 实现 |
| 金额以「分」为单位 | 实测返回 `2790` | `Money` 类统一以分存储 |
| `list-nutrition-foods` 返回自定义 DSL 而非 JSON | 实测解析失败 | 实现按行解析器 |
| `available-coupons` 返回 Markdown 而非 JSON | 实测解析失败 | 实现文本提取 + 降级 |
| 响应体 JSON 提取会误抓嵌套对象 | `query-nearby-stores` 解析到 `reservationTimeOptions` 的元素 | 用 `raw_decode` + 要求顶层含 `success`/`code`/`data` |
| 品类名含换行符（`"鸡肉汉堡\n/卷"`） | 饮品识别失效 | 增加文本清洗 |
| 单杯饮料被当成一顿正餐推荐 | 真实输出推荐了「雪碧小杯」 | 增加饮品识别与降权 |
| 组合规划把三杯饮料当两人正餐 | 真实输出「纯悦+雪碧+热牛奶」当午餐 | 组合必须含正餐基底 |
| 口语场景词未识别 | 用户问「30元以内晚上吃什么」，「晚上」不在场景词表，场景分恒为中性 6 分 | 补全早/中/晚/夜宵/聚会的口语变体 |
| 排除过滤完全失效 | 静态审查发现 `item.category or "" + tags` 因运算符优先级丢弃 tags，说「不吃辣」过滤不掉 tag 含「辣」的商品 | 改为复用统一的 `matches_exclusion`，修正括号 |
| 负数预算被翻转 | 模糊测试发现 `-50元` 解析成 5000 分，硬预算反而被放宽 | 正则加负号 lookbehind，排除异常金额区间 |
| 中文数字算错 | 「三十」解析成 40、「十五」解析成 105、「一百」无法识别 | 重写为按段累加算法，并修正「十」在两个字典中重复定义的问题 |
| 货币符号前置不识别 | 用户打「¥30」「￥30」时预算被完全忽略 | 单独处理符号在前的形式 |
| 异常人数与金额 | 「0个人」「100个人」行为不一致，「999999元」扰乱排序 | 增加人数与金额的合理区间校验 |
| 带娃家庭人数识别失败 | 「两大一小」「三口人」「一大家子」全部识别为 1 人，三口之家被当单人推荐 | 新增组合表达解析、口计数、家庭聚餐估计 |
| 省略单位的预算不识别 | 「150以内」「预算150」「最多150」完全无法识别（正则要求数字后必须跟单位字） | 增加省略单位的形式 |
| 健身诉求不识别 | 「高蛋白」「低脂」「低卡」「扛饿」全部不认识 | 补充健康取向词表 |
| 营养诉求识别了却用不上 | 口味匹配只看文本，而商品名里不写「高蛋白」，导致所有候选都是 0 分 | 营养类偏好改用真实营养数据判定 |
| 营养字段名拼写错误 | 写成 `energy`（实际 `energy_kcal`），getattr 返回 None，低卡/饱腹偏好静默退化成最低分 | 修正字段名并加字段存在性断言测试 |
| 过敏类表述不识别排除项 | 「痛风，不能吃海鲜」「乳糖不耐」「坚果过敏」中的食材无法被识别为排除项 | 重写排除项提取，覆盖显式否定/医疗表述/间接否定三类 |
| 食材同义词缺失 | 用户说「不吃奶」，商品名写「吉士」「芝士」「奶昔」，导致乳糖不耐用户收到芝士堡 | 新增食材同义词映射表 |
| 医疗饮食限制不识别 | 「医生说要低蛋白」完全不被识别为偏好，肾病用户被当成没提要求 | 补充低蛋白/低钠/控糖等医嘱级词表 |
| 低蛋白用户收到甜品 | plan_combo 只按价格排序，无视营养诉求，把冰淇淋配进了低蛋白用户的正餐 | 组合规划增加健康取向过滤 |
| 真实业务数据可能入库 | 数据快照含麦当劳实时菜单与价格 | 加入 .gitignore，改为运行时生成 |

最后一条尤其典型：**只有拿真实数据跑，才会发现「15元预算下推荐一杯雪碧」这种荒谬结果。**
